# 2026.241.1930 — feat: punktfunk check verb plugin

## Summary

Adds the `punktfunk:` check verb — an out-of-tree, out-of-process plugin that drives a
running [punktfunk](https://git.unom.io/unom/punktfunk) streaming host through its
management REST API. It is the management half of punktfunk support in charly; the host
itself is installed by [`layer-punktfunk`](https://github.com/opencharly/layer-punktfunk).

30 methods, split read/write:

| Group | Methods |
|---|---|
| host / health | `health` `status` `diagnostics` `diagnostics-refresh` `compositors` `gpus` `plugins` `hooks` |
| native pairing | `pair-status` `pair-arm` `pair-disarm` `pending` `approve` `deny` `pin` |
| paired clients | `clients` `rename` `access` `unpair` |
| library | `library` `scanners` `scanner-toggle` |
| virtual displays | `display-state` `display-monitors` `display-settings` `display-release` |
| lifecycle | `actions` `action-invoke` `end-game` |
| stream | `events` (bounded SSE) |

No edit to `charly/` or `spec/` is needed: `checkVerbProviderBijection` explicitly allows
out-of-tree verbs, and `punktfunk` collides with no authored `#Op` field.

### Why this is not the generic `http:` verb (R3)

`http:` already does URL + status + body/header matchers + `allow_insecure`, and
duplicating that would be pointless. This verb exists for what `http:` structurally cannot
do:

- **Token discovery.** The bearer token is generated per host at first start and written
  inside the venue. An authored `http:` step cannot read a per-deploy secret out of a
  container or guest.
- **Domain semantics.** Methods map to endpoints and return real verdicts, with
  `json_path:` to assert one field rather than pattern-matching a JSON blob.
- **`events`.** A bounded SSE subscription is the only way to assert a *transition*;
  polling `/api/v1/host` observes a state, never that a stream started.

### Three design decisions worth reviewing

**1. The request is issued from inside the venue, not from the charly host.** punktfunk
binds its management API to loopback by default and its documentation is explicit that the
API stays loopback-only while the web console is the network-facing surface. A host-vantage
`cc.HTTPDo` cannot reach a loopback-bound listener in a container, and the two ways to make
it reachable — republishing the port, or a socat eth0→loopback relay — would both weaken
exactly the posture upstream chose. Probing in-venue keeps that intact and puts the request
on the same side as the token. The cost is a `curl` dependency, so its absence is reported
as a precise, actionable message rather than a bare exit code (tested).

**2. The token never touches argv.** It travels through `curl --config` on stdin, via a
heredoc with a quoted delimiter so the shell cannot expand it. argv is world-readable
through `/proc`, and a management token in `ps` output would be a real leak on a shared
host. `TestTokenNeverReachesArgv` pins this.

**3. The TLS flag is `verify_tls`, not `insecure`.** punktfunk serves a self-signed
certificate, so verification must be off by default. A Go bool cannot distinguish "unset"
from "false", so an `insecure` field could never default to true — inverting the name makes
the ZERO VALUE the correct default instead of relying on a tri-state that does not survive
codegen.

Mutating methods are refused in a `check:` step (via `Op.IntentDo == assert`, which the
runner stamps from the step keyword and authors cannot set), so a probe can never silently
unpair a device or reboot a machine.

### A doc-vs-reality divergence the live run caught (R1)

The first live run failed three of five verb checks with a clean **HTTP 401**:

```
FAIL  [pf-verb-status]  punktfunk: status: HTTP 401: {"error":"missing or invalid credentials (a paired client cert, or a bearer token)"}
```

Root cause, measured in the venue rather than guessed: the management-token file is **not**
a bare token, which is what the upstream documentation implies ("generated and persisted
API token … path=~/.config/punktfunk/mgmt-token"). Against punktfunk-host 0.33.0-1 it is an
env-file line:

```
$ cat ~/.config/punktfunk/mgmt-token
PUNKTFUNK_MGMT_TOKEN=<64-hex-token>
```

The plugin was sending the whole line as the bearer. Fixed with a real parser
(`token.go`) that accepts both the env-file and bare forms and prefers the
`PUNKTFUNK_MGMT_TOKEN` key — the host writes a sibling `plugin-token`, so key preference is
load-bearing rather than cosmetic. `TestParseTokenFile` covers the measured shape,
quoting, CRLF, comments and the multi-key ordering both ways.

No schema check would have found this. It is the concrete reason the verb was proved on a
live bed before landing rather than after.

### The stock plugin CI gate is empty — this repo's is not

While setting this up I measured that running `charly box validate` at a **plugin repo
root** validates nothing: a plugin repo has no project `charly.yml`, so discovery never
reaches `candy/<name>/charly.yml` and the command exits 0 on any manifest. Injecting a
malformed provider class (`notaclass:punktfunk`) still exited 0 at the repo root, while the
same manifest under a project with a `discover:` block failed correctly:

```
plugin.providers.0: invalid value "notaclass:punktfunk" (out of bound =~"^(kind|deploy|verb|…):[a-z0-9][a-z0-9_-]*$")
```

**Where the fixed gate lives, precisely:** this repo's `deploy.yml` already carries the
corrected shape — it stages a minimal project with a `discover:` block so the manifest is
actually parsed, and additionally runs `go build` / `go vet` / `go test` / `gofmt -l`, the
substance of a plugin repo that the stock template omits entirely. **It is not in this
diff.** It was installed on `main` during repo bootstrap, together with the `pr-validator`
and `tag-on-merge` dispatchers, because `tag-on-merge` fires on `workflow_run` and
`workflow_run` only fires for workflows already present on the default branch — a first PR
that *installed* the dispatcher could never be tagged by it. So the gate that produced the
green `build` check on this PR is the corrected one, and this PR's 16 files are the plugin
module itself. Every step of it was dry-run locally before being installed.

The same weakness affects the other plugin repos still on the stock template. It is
tracked as **opencharly/charly#459**, which carries the measurement, the control against
`plugin-vnc`, and the concrete template fix; this repo is named there as the reference
shape. That is the exit — this PR advances it by shipping and proving the corrected gate.
