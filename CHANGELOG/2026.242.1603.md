# 2026.242.1603 — fix(punktfunk): make the mutating half work, and pairing expressible

## Summary

Makes the **mutating half** of the `punktfunk:` verb work, and makes an unattended two-system pairing expressible. Every defect here was found by running the flow — and the first meant no mutating method had ever succeeded against a real host.

### 1. A bodyless mutating request needs `Content-Type` **and** a body

`curlRequest` emitted `Content-Type` only when a body was present, and the mutating methods that take no authored input (`pair-arm`, `approve`, `deny`, `end-game`, `diagnostics-refresh`, `action-invoke`, `scanner-toggle`, `display-release`) send none — so they arrived with neither. Three distinct live responses against `0.33.0-1`, `POST /api/v1/native/pair/arm`:

```
no Content-Type          {"error":"Expected request with `Content-Type: application/json`"}
Content-Type, no body    {"error":"Failed to parse the request body as JSON: EOF while parsing …"}
Content-Type and `{}`    {"enabled":true,"armed":true,"pin":"8155","expires_in_secs":119,…}
```

**Why it was invisible:** every check shipped before this calls a READ method. The mutating half had never run against a real host — the same blind spot that let single-node beds report green while nothing was ever paired.

### 2. `pin_out` / `pin_file` — the PIN has to travel

The host **generates** the PIN and ignores a caller-supplied one (`{"pin":"424242"}` came back as a different, host-chosen pin), only the client can use it, and charly has no mechanism to carry a step's output into another step's input. `pair-arm` can now drop it at a path both members mount, and `pair` reads it there. The venue's own shell pipes the file into `--pin -`: the value never reaches argv and never passes through this process.

Console approval is not an alternative — `pair` with no PIN reports `no --pin and no terminal to ask on`.

### 3. Address resolution for every host-taking method

`punktfunk pair` rejects a hostname with `InvalidArg("host:port")` where `reachable` accepts the same name. And `pair` files the host under the **address** it paired with:

```
$ punktfunk hosts list
10.89.0.163   10.89.0.163:9777   paired   -
```

so a later `speed-test <name>` is told the name "isn't a saved host". Resolution therefore happens in one place for every method that takes a host-ref, keeping the saved key and all later references identical — and letting a bed name its peer by member name throughout.

### 4. Diagnostics that name themselves

Three failures cost an iteration each purely because they were unreadable, so each is now legible at the source:

- The client reports failures on **stdout**, not stderr — `Pairing failed: InvalidArg(…)`, `client identity: HOME unset…`. Reporting only stderr left a bare `exit 1`.
- `HOME` is unset in charly's exec channel and the client stores its identity under it. Derived from passwd when absent.
- `test -s FILE && …` exits 1 **silently** when the guard fails, indistinguishable from the client failing. Replaced by a branch that names the condition.

Guards cover the write shape, the provider's decision to supply `{}`, reads staying bodyless, `writePinOut` (write shape plus three failure modes), `pin_file` reaching stdin via the venue shell, the lookup running outside the PIN pipeline, HOME being ensured for every client call, the client's message surfacing, and uniform host resolution.

**Two guards were themselves wrong and are fixed.** `TestOnlyPairResolvesTheHost` asserted the opposite of the correct rule and passed while the bed failed exactly as that rule predicts. And `TestPinFileIsPipedIntoPunktfunkNotTheLookup` keyed on the *first* pipe, which broke as soon as the HOME fallback introduced one of its own — it now anchors on the client invocation.

## The one thing this does not prove

`speed-test` is **not** asserted, because the headless client advertises no video codec and the host refuses every session:

```
no shared video codec: client advertised 0x00, host can emit 0x01
```

That is not parked. It is routed to the named batch **`punktfunk-client-codec-negotiation`** (opencharly/plugin-punktfunk#8), which records the six hypotheses tested and eliminated — GPU absent (no: `DRINODE` is injected), no H.264 decode (no: `vainfo` reports `VAProfileH264Main: VAEntrypointVLD`), missing packages, `mesa`/`vulkan-radeon` (unlandable, `mesa-git` conflict), `PUNKTFUNK_DECODER` (no effect on any of three values), and a missing renderer (a headless compositor changed nothing). Upstream's docs state the headless client's codec negotiation in containers is unspecified.

So this PR claims a proven two-system **pairing**, and claims nothing about streaming.
