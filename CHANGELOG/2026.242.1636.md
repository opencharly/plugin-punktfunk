# 2026.242.1636 — fix(punktfunk): give the renderer a display — punktfunk is not the streaming client

## Summary

**`punktfunk` is not the streaming client.** The package ships three binaries and I had been
driving the wrong one all along:

```
$ pacman -Ql punktfunk-client | grep bin/
/usr/bin/punktfunk          <- control CLI
/usr/bin/punktfunk-client   <- the streaming renderer
/usr/bin/punktfunk-session

$ ldd /usr/bin/punktfunk
	linux-vdso.so.1 / libgcc_s.so.1 / libm.so.6 / libc.so.6 / ld-linux-x86-64.so.2

$ ldd /usr/bin/punktfunk-client | grep -cE 'vulkan|wayland|drm|gbm'
6      (of 137 objects: libvulkan.so.1, libwayland-client/egl/cursor, libdrm, libgbm)
```

`launch` and `open` spawn that second binary, and it is a Wayland client. charly's exec
channel sets no display, so a venue that **has** a compositor still failed as the CLI's
opaque exit 4 ("renderer startup failed") with nothing saying why.

### 1. Derive the display, the way `HOME` is already derived

`WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR` are now resolved from the socket the compositor
actually created, and only when the venue did not supply them, so an explicit setting always
wins. It runs BEFORE the pipeline — same rule the PIN pipe and the host lookup follow, since
an export inside a pipeline lands in a subshell and never reaches the client.

A venue with no compositor fails **there**, naming what was searched, and keeps exit 4 so the
documented meaning survives:

```
punktfunk: no wayland display in this venue (searched "", /run/user/1000, /tmp) - the renderer cannot start
```

### 2. `speed-test` does not prove streaming, and its comment said it did

The old comment called it "the assertion that the transport actually carries". It cannot be.
It runs on the control binary, so it advertises codec `0x00` and a host that requires a video
codec refuses the session:

```
no shared video codec: client advertised 0x00, host can emit 0x01
```

That is the client accurately reporting what it is — not a host defect, and not the upstream
bug I filed it as. See opencharly/plugin-punktfunk#8, which is corrected in place. `launch`
is the method that proves streaming, because it spawns the renderer.

**Negative control** — the new guards fail on the thing that matters. Dropping
`NeedsDisplay` from `launch`:

```
--- FAIL: TestOnlyRendererMethodsCarryTheDisplayPrologue
    launch: NeedsDisplay = false, want true
    launch: script carries the display prologue = false, want true
--- FAIL: TestDisplayPrologueRunsBeforeThePipeline
```

Three guards: only renderer methods carry the prologue (and non-renderer methods must NOT
acquire an exit-4 guard they can never satisfy), it precedes the client invocation, and it
fails with the documented code while naming the condition.
