# 2026.243.0603 — docs(punktfunk-skill): delete the map-form workaround — charly#471 is fixed

## Summary

The skill instructs every reader to avoid the scalar shorthand:

```
punktfunk: status          # FAILS the project parse today
…
Tracked as opencharly/charly#471. Until it is fixed, always use the map form.
```

**charly#471 was fixed by charly#473 on 2026-08-30.** The workaround outlived the defect, and a
skill that routes around a bug which no longer exists teaches the wrong thing to everyone who reads
it — which is also why `opencharly/marketplace#254` is BLOCKed on R4a, since the corpus republishes
this text verbatim.

## Root cause of the original defect (for the record)

`prescanRemotePluginManifests` — the leg that reads `@github` plugin refs — sat behind
`prescanDeclaredPluginWords`'s early return for a missing local `discover:` block. The two are
unrelated, so a project that pinned a plugin remotely and discovered nothing locally never
prescanned it, and its `plugin: primary:` never reached the parse.

## How tested

authoring the sugar:

```yaml
probe-box:

    pod:
        image: probe-box
        plan:
            - check: scalar sugar reaches the parse for a remote-pinned plugin candy
              punktfunk: health
```

| charly | result |
|---|---|
| `v2026.242.0649` (pre-fix) | **fails** — `plugin verb "punktfunk" takes a MAP input (it declares no primary field for the scalar shorthand)` |
| `main` `0443e07` (post-fix) | **exit 0** |

**A liveness control, because a scratch-project `validate` can pass vacuously.** Swapping the verb
for a bogus one on the *passing* charly still errors:

```
node "probe-pod": plan[0] plugin verb "notaverb" takes a MAP input (…)
```

so the step really is being parsed, and the exit 0 above is a result rather than an absence of
checking.

**A false start worth recording:** my first "pre-fix" control was `v2026.242.0711`, which passed —
because charly#473 merged at `07:11:46`, so that tag *contains* the fix. The A/B only means
something at `v2026.242.0649`.

**This repo's own gate**, at the charly its CI actually pins (`v2026.241.1535`, built from source
exactly as `.github/workflows/deploy.yml` does), on the final committed tree:

```
$ charly box validate ; echo "VALIDATE_EXIT=$?"
VALIDATE_EXIT=0
```

## What the scalar switch does NOT gate

The candy's own check now uses the shorthand it documents. That is documentation-by-example, **not**
a regression gate, and the manifest says so:

> in THIS repo the candy is discovered locally from `candy/`, and the sugar always worked on the
> local path — #471 only ever affected an `@github`-pinned candy. So the repo's own `box validate`
> cannot catch a regression of the remote leg; only a consumer that pins this candy remotely can.

Measured, not assumed: the pre-fix charly validates *this repo* at exit 0 while failing the remote
fixture above. I initially wrote the comment claiming this check would gate the remote leg, and the
control disproved it before it shipped.

**Consequently the CI charly pin is left alone.** Bumping it looked necessary while I believed the
scalar form needed a post-fix charly here; once the local path was shown to work on the old pin, the
bump became unexplained scope and was reverted.
