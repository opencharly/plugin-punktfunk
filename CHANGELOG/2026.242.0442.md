# 2026.242.0442 — fix: add a root charly.yml so the candy CI gate is real

## Summary

Makes this repo's candy CI gate actually gate something, and reverts the workaround it was
carrying.

Without a root `charly.yml` a plugin repo is **project-less**: charly scans **no candies at
all**, so the stock `charly box validate` step exits 0 on any manifest — including one with
a malformed `plugin.providers` entry (opencharly/charly#459).

A four-line `discover:` block is the whole fix. Because the stock step now works, `deploy.yml`
drops the staged-project workaround it carried and goes back to plain
`charly box validate`, keeping only the `go build` / `go vet` / `go test` / `gofmt` steps the
stock template omits.

## How tested

**The gate now catches what it previously waved through** — same repo, same command, only
the root manifest differing:

```
# pristine manifest
$ charly box validate
exit=0

# with `- verb:punktfunk` changed to `- notaclass:punktfunk`
$ charly box validate
charly: error: command "validate": 2 validation errors:
  candy "plugin-punktfunk": CUE schema: .../candy/plugin-punktfunk/charly.yml:
  candy "plugin-punktfunk": 2 errors in empty disjunction:
```

Before this PR that same malformed manifest exited **0**.

**The mechanism, isolated with a plain layer** (so `box list candies` can see it — it
filters plugin candies, which is why it is not a usable probe on its own):

```
# no root charly.yml
$ charly box list candies         # (nothing — not scanned at all)
$ charly box validate             # exit 0 even with a bogus field

# with the 4-line root charly.yml
$ charly box list candies
plainlayer [testing]
$ charly box validate
... notafield: field not allowed
```

So it is not that the gate skips validation — the repo simply has no candies to validate.

**Consumers are unaffected**, which was the real risk of adding a root manifest: a consuming
project might resolve the candy twice (once via the pinned subpath ref, once via the new
`discover:`) and conflict. Tested by putting the root manifest into the *fetched* checkout
that `opencharly/distro-cachyos` resolves for
`@github.com/opencharly/plugin-punktfunk/candy/plugin-punktfunk:v2026.241.1930`, then
validating that project both ways:

```
# cached checkout WITHOUT the root manifest
$ charly box validate            # exit 0

# cached checkout WITH the root manifest
$ charly box validate            # exit 0
Warning: box "punktfunk-host" includes candy "github.com/opencharly/layer-punktfunk"
with a packaged-only service (no custom-exec sibling), but composition does not
preserve_user (its systemd unit will be ignored)
```

Identical outcome either way — the root manifest declares no entities, so it changes what
`charly` does *in* the repo and nothing about how the repo is consumed. The cache was
restored afterwards.

### The warning in that output, root-caused (R1)

It is emitted in **both** arms, so it is not caused by this change — but it is real, and
"pre-existing" is not a disposition. Root cause: the punktfunk candy gives
`punktfunk-host` two service forms (a packaged systemd user unit **and** a container
`exec:` wrapper, because supervisord cannot run a user unit), but `punktfunk-web` and
`punktfunk-scripting` are **packaged-only**. On a container venue those two are silently
dropped — which is exactly what the warning says.

It matters because the candy declares `https+insecure:47992` unconditionally, so a pod
deploy publishes the console port with nothing listening on it. The systemd venue is
unaffected; `check-punktfunk-vm` enables all three units.

The fix is a product decision — give the console a container `exec:` sibling, or stop
advertising its port on that venue — and it belongs in the candy, not in this repo's CI
configuration. Routed to **opencharly/layer-punktfunk#4**, which carries the service
table, the port consequence and both options.
