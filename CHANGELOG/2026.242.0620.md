# 2026.242.0620 — fix: author the punktfunk verb in map form, and say why

## Summary

The candy's own ADE check and the skill's examples used the **scalar shorthand**
(`punktfunk: health`). That shorthand relies on `plugin.primary:` being read before any
plugin connects — which works for a locally discovered candy and is **silently ignored when
the candy comes from an `@github` ref**, i.e. how every real consumer pins it.

The parse then rejects the step:

```
plugin verb "punktfunk" takes a MAP input
(it declares no primary field for the scalar shorthand)
```

and the failure is **not local to that step** — it blocks the parse for every bed sharing the
project closure. Authoring the shorthand in one bed took down `check-agentteams-snapshot`,
`check-boxload-pod` and `check-sidecar-pod` until the steps were rewritten
(opencharly/distro-cachyos#38).

This converts the candy's own check and the skill's examples to the map form, and documents
the limitation with its tracking issue instead of leaving the skill teaching something that
fails.

Tracked as opencharly/charly#471.

## How tested

The behaviour was isolated with a controlled A/B — same candy, same authored step, same
project shape, differing only in how the candy is referenced:

| arm | reference | `charly box validate` |
|---|---|---|
| A | `@github.com/opencharly/plugin-punktfunk/candy/plugin-punktfunk:v2026.241.1930` | **fails** with the message above |
| B | `plugin-punktfunk`, discovered from `candy/` | **exit 0** |

Arm B is the byte-identical candy cloned from that same tag, so the manifest is correct and
the declaration is understood — it just never reaches the parse when the candy is remote.

**This branch validates**, under a binary built from the tag this repo's CI pins
(`v2026.238.1242`):

```
$ charly box validate
VALIDATE_EXIT=0
```
